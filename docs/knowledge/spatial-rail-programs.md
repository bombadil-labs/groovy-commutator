# Editable spatial Rail programs preserve recursive evolution and program transport

An eight-bit ECA program gains one Rail selector wrapper per added dimension. A fixed five-symbol, radius-nine physical interpreter stores the eight leaf bits in actual program cells beside a data cell. The same layout recipe lays the word along each new spatial axis.

A separate identity guard program (204) keeps the off-interface zero/one backgrounds stable. The complete program-and-data evolution then commutes through both dimensional interfaces, for every ECA starting program and arbitrary heterogeneous native fields. The local proof extends to every finite number of lifts.

One instruction edit changes one physical program symbol. A separately frozen extension also preserves autonomous state-gated copying of whole program words from the left neighbor. The [note](../research/2026-09-09-spatial-rail-programs.md) contains the physical interpreter, proofs, failed repeated-program baseline, rescue, and reproducible audits.

The canonical layout uses 9^d cells per logical cell, including nine occupied symbols. Tags, wrapper structure, and infinite guard backgrounds are explicit architectural resources. The result does not establish binary radius-one realization, arbitrary program synthesis, marker self-organization, or ternary correction-role execution.
